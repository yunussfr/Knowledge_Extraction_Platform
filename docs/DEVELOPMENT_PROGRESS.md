## Current Phase Plan

### Phase 0 — Environment and Baseline

- Expected files: `docs/DEVELOPMENT_PROGRESS.md`, a minimal reproducible environment specification if the legacy `requirements.txt` cannot serve that role, and baseline artifacts under a non-user dataset path.
- Models/contracts affected: none; Phase 0 must establish the existing behavior without pulling later architecture phases forward.
- Validation order: clean-environment install, targeted import check, full offline test suite, deterministic mock pipeline, optional live checkpoint only when credentials and opt-in conditions are satisfied, then baseline metric capture.
- Migration risks: the tracked `venv/` points to a missing Python 3.11 installation; `requirements.txt` is wrapped in triple quotes and contains a broad environment freeze; `.env` contains provider credentials that must never be printed; existing `knowledge/` artifacts must not be overwritten.

### Phase 1 — Policy-Aware Gold Evaluation Set

- Expected files: fixed JSON fixtures under `tests/evaluation/fixtures/`, provider-neutral metric functions under `src/evaluation/`, an offline benchmark command under `scripts/`, Phase 1 tests, and a saved baseline under `docs/baselines/`.
- Contracts affected: benchmark-only source cases keyed by policy, extraction pages with manually known records and field evidence, prediction envelopes, and deterministic metric result dictionaries. Runtime `AgentState` and provider contracts remain unchanged in this phase.
- Required coverage: 20–30 source candidates, at least two policies over the same candidates, 5–10 extraction pages covering every Phase 1 scenario, all named source/extraction metrics, and proof that the same source can have different expected outcomes by policy.
- Validation order: fixture integrity, metric unit cases, exact saved-baseline comparison, two-run reproducibility check, then full offline regression suite.
- Migration risks: Phase 9 policy-aware runtime evaluation and Phase 15 multi-record extraction do not exist yet, so the Phase 1 baseline must truthfully model current deterministic legacy behavior without implementing those later phases early.

### Phase 2 — SourcePolicy and Request Configuration

- Expected files: typed request-policy models in the existing schema layer, deterministic request parsing/normalization in the existing config loader, optional policy/domain examples in both request YAML files, and focused unit tests under `tests/unit/`.
- Contracts affected: `SourceImportance`, `SourcePolicy`, typed domain/source controls, and a normalized request model that preserves `None` for absent hard restrictions while using empty lists only for soft preferences.
- Required tests: neutral, preferred-only, allowed-only, blocked-only, desired-only, avoided-only, technical-depth-heavy, omitted minimum depth, allow/block conflict, and all optional source-type fields omitted.
- Migration risks: current configs use `research.reference_urls` and `research.preferred_domains`; compatibility must be preserved while introducing canonical `sources.seed_urls` and source policy fields. Runtime source-search behavior is Phase 3/6/9 work and must not be pulled forward beyond deterministic normalization.

### Phase 3 — ResearchPlanner Contract Integration

- Expected files: planner input/query-family Pydantic contracts, serializable policy state, a deterministic input builder in the existing planner node, and focused planner-boundary tests.
- Contracts affected: `ResearchPlannerInput`, optional `ResearchQueryFamily` support in `ResearchPlan`, and `AgentState.source_policy`.
- Required behavior: topic/purpose/policy/seed/domain context reaches the planner; `None` hard restrictions remain `None`; query and family duplicates are rejected or normalized deterministically; no prompt wording changes.
- Migration risks: the live provider previously omitted `research_topic`; Phase 3 must not hide provider contract errors or modify the user-managed prompt to compensate.

### Phase 4 — Web Provider Abstraction

- Expected files: `src/tools/web/` internal models, discovery/acquisition protocols, Firecrawl adapters, a deferred Crawl4AI provider boundary, provider factories, migrated discovery/acquisition nodes, and offline provider-contract tests.
- Contracts affected: provider-neutral discovered source and acquired document models; `SourceDiscoveryProvider` and `WebAcquisitionProvider` protocols.
- Required behavior: nodes receive only internal Pydantic contracts; legacy Firecrawl search/scrape remains available behind adapters until Crawl4AI migration is proven in Phase 5.
- Migration risks: Crawl4AI dependency and real acquisition belong to Phase 5, so Phase 4 may define its boundary but must not claim a working Crawl4AI integration prematurely.

### Phase 5 — Crawl4AI Single-Page Acquisition

- Expected files: pinned Crawl4AI dependency, provider implementation in `src/tools/web/crawl4ai_provider.py`, explicit settings/env documentation, local HTML fixtures and provider tests, and factory migration from the legacy acquisition adapter.
- Contracts affected: `AcquiredDocument` normalization only; downstream nodes continue receiving the Phase 4 internal contract.
- Required fixture coverage: normal, empty, noisy, Turkish/Unicode, headings, lists, tables, duplicate content, and provider failure.
- Validation order: package/import diagnostics, mocked result normalization, real local/raw HTML fixture acquisition, targeted node tests, full offline suite, baseline regression.
- Migration risks: Crawl4AI 0.9.x is async and browser-backed while the current LangGraph is synchronous; the provider must own lifecycle bridging and must not leak crawler objects into state.

### Phase 6 — Candidate Registry and URL Normalization

- Expected files: candidate/origin contracts in the schema layer, a conservative URL-normalization and registry component, source-search integration, serializable candidate state, and focused unit tests.
- Contracts affected: `DiscoveryOrigin`, canonical `SourceCandidate`, discovery-origin history, seed markers, preview/evaluation/selection state, and rejection reasons. Existing downstream candidate dictionaries require a bounded compatibility projection during migration.
- Required behavior: repeated URLs from different queries collapse into one canonical candidate; every query origin survives; seed and search origins coexist; canonical counts drive metrics; registry state prevents duplicate preview work without imposing policy filters.
- Validation order: URL normalization edge cases, registry upsert/origin merge cases, seed-plus-search cases, duplicate-work guard, source-search integration, full offline suite, then Phase 0/1 baseline regression.
- Migration risks: URL normalization must be conservative and must not merge meaningfully distinct resources; seed URLs remain references rather than implicit allowlists; existing evaluator state/checkpoints must remain serializable and readable.

### Phase 7 — Crawl4AI SourcePreview

- Expected files: a bounded preview implementation in the Crawl4AI provider, a `source_preview_node.py` between search and evaluation, preview/cache settings, serializable `source_previews` state, graph integration, local-fixture tests, and evaluator-boundary tests.
- Contracts affected: existing `SourcePreview` fields, registry `preview_status`, and evaluator input only. Full `AcquiredDocument` acquisition remains after schema approval.
- Required behavior: prefer fit/clean Markdown with raw fallback; cap preview text deterministically; populate headings, word counts, links, language/date/structure hints when observable; cache by canonical URL; preserve per-source failures and continue; send real bounded preview evidence to SourceEvaluator.
- Validation order: pure preview normalization/bounds, cache hit and failure cases, local Crawl4AI fixtures, preview-node registry integration, evaluator payload inspection, full graph/default suite, then Phase 0/1 baselines.
- Migration risks: preview must not become full extraction, must not perform unbounded crawling, and must not make one failed page abort evaluation of all remaining candidates. Mock mode must stay deterministic and network-free.

### Phase 8 — Bounded Crawl4AI Site Exploration

- Expected files: typed `site_exploration` request config, a bounded provider implementation of `explore_site`, a serializable `site_exploration_node.py`, registry-origin integration, explicit state fields, graph wiring, and cyclic local-site fixtures/tests.
- Contracts affected: `DiscoveredPage`, `DiscoveryOrigin(method="site_exploration")`, canonical `source_registry`, and explicit exploration attempt/result state. No SourceSelector or AdaptiveCrawler contract is introduced.
- Required behavior: enforce `enabled`, `max_seed_domains`, `max_depth`, `max_pages_per_domain`, same-domain scope, and URL filtering before/while traversal; normalize every discovered URL; deduplicate links and exploration starts; terminate on cycles; preserve parent/depth origin context.
- Validation order: config boundaries, pure traversal limits using fixture graphs, duplicate/cycle cases, provider normalization, registry integration, opt-in local Crawl4AI proof where supported, full graph/default suite, then Phase 0/1 baselines.
- Migration risks: newly explored candidates must not be treated as already evaluated/selected; current graph can update the registry before later Phase 9/10 evaluation/selection migrations, but it must never silently include unexplored or out-of-scope pages in acquisition.

### Phase 9 — Policy-Aware Source Evaluation and Characterization

- Expected files: extensible `SourceProfile`/`EvaluatedSource` contracts, deterministic hard-rule enforcement and soft-score helpers, evaluator input/output migration, registry evaluation linkage, benchmark-aware mock fixtures, and focused policy tests. No separate classifier node or prompt edit.
- Contracts affected: source type/content characteristics/depth/authority signals and reusable density/technical/recency/extractability scores; request-specific relevance/alignment/final score, decision, reasons, and hard-policy rejection. Existing selected/rejected projections remain until Phase 10 selection migration.
- Required behavior: enforce allowed/blocked domains/types and minimum depth only when explicitly configured; use preferred types/domains, desired/avoided content, and importance as ranking signals only; preserve preview failure; allow the same source profile to score differently by policy; avoid universal official/authority bonuses.
- Validation order: typed contracts and score bounds, explicit hard-rule matrix, neutral-policy invariance, soft preference non-rejection, technical-depth counterexample, same-source multi-policy score, preview-failure visibility, source gold benchmark comparison, full graph/default suite, then baselines/checks.
- Migration risks: current system prompt output schema is user-managed and may not yet return the richer model. Phase 9 must adapt the provider boundary without changing prompt wording or inventing profile facts absent from real preview/evaluator output.

### Phase 10 — Source Selection and Diversity

- Expected files: a deterministic `source_selector_node.py`, explicit selection settings/contracts if needed, graph edge migration, registry selection updates, selection metrics, and focused diversity tests. SourceEvaluator remains characterization/evaluation only; no prompt edits.
- Contracts affected: selected-source compatibility projection, `selection_state`, and explainable selection reasons/rank. `EvaluatedSource` remains the authoritative input; hard-rejected or preview-failed sources are ineligible.
- Required behavior: rank eligible sources by final score while considering information density, technical depth when important, extractability, canonical duplicate state, domain diversity, and useful source-type diversity; preferred type stays soft; never let one domain dominate blindly; respect `max_sources`; report unique-domain counts correctly.
- Validation order: eligibility/hard-reject filter, stable score ordering, one-domain pressure, preferred-type alternative, source-type diversity signal, max-source bound, canonical metrics, graph integration, frozen benchmark comparison, full suite, then baselines/checks.
- Migration risks: exploration pages added after initial evaluation remain pending and cannot be selected until evaluated; diversity must not force low-quality sources merely to satisfy a quota, and the selector must not reinterpret optional preferences as constraints.

### Phase 11 — Evidence-Aware Dataset Schema Design

- Expected files: an explicit schema-designer input contract, representative selected-preview projection, schema-designer node boundary updates, checkpoint/resume preservation tests, and README/progress evidence. System prompt wording remains untouched.
- Contracts affected: dataset topic/purpose, `ResearchPlan`, `SourcePolicy`, selected `SourcePreview` evidence, explicit schema constraints, and draft-schema state/checkpoint continuity. Provenance remains metadata rather than normal domain fields.
- Required behavior: the designer receives real evidence only for final selected sources, maintains human approval, keeps full research/source state through editable resume, and does not invent required schema fields unsupported by the request/evidence boundary.
- Validation order: typed input construction, selected-preview filtering, request/policy/constraint payload inspection, provenance-field separation, approval wait, checkpoint round-trip, full suite, then prior baselines/checks.
- Migration risks: legacy checkpoints may lack Phase 10 selection fields; input construction needs a clear compatibility path without treating every candidate preview as selected evidence or changing owner-managed prompt text.

### Phase 12 — Crawl4AI Multi-Source Acquisition

- Expected files: bounded batch-acquisition settings/contracts, Crawl4AI provider concurrency/throttling/failure-isolation implementation, acquisition-node migration, and provider/node tests. Bronze/raw content must remain separate and observable.
- Contracts affected: `WebAcquisitionProvider.acquire_many`, ordered per-source `AcquiredDocument` results, batch metrics/state if required, and existing compatibility `scraped_documents` projection.
- Required behavior: acquire final selected sources only after schema approval; enforce bounded concurrency and throttling; isolate individual failures; preserve input order, raw/fit content, cache metadata, and per-source errors; avoid a crawler/client object in state.
- Validation order: configuration bounds, deterministic batch ordering, concurrency cap, throttle behavior, mixed success/failure, acquisition-node integration, real local multi-source proof, full suite, then baselines/checks.
- Migration risks: Phase 5 intentionally used sequential single-page crawler lifecycles; changing concurrency can stress Windows browser process startup and must not turn per-source errors into a batch-wide exception or violate provider isolation.

### Phase 13 — Deterministic Content Processing

- Expected files: provider-neutral deterministic Markdown/content normalization helpers, processing-node Bronze→Silver migration, thin/empty-page outcomes, and fixture tests for headings/lists/tables/boilerplate/Unicode.
- Contracts affected: Silver processed-document representation, processing status/failure details, content/hash provenance linkage, and existing `clean_documents`/`processed_data` compatibility surfaces.
- Required behavior: normalize whitespace and reduce clear boilerplate without losing headings, lists, tables, source text evidence, or Unicode; detect empty/thin pages explicitly; preserve Bronze raw/fit content unchanged.
- Validation order: pure normalization fixtures, structure preservation, boilerplate counterexamples, empty/thin detection, idempotence, processing-node integration, extraction-fixture regression, full suite, then prior baselines/checks.
- Migration risks: aggressive cleanup can destroy evidence or table/list structure; Phase 13 must remain deterministic and cannot use an LLM or overwrite `acquired_documents`/raw Markdown.

### Phase 14 — Extraction Router

- Expected files: typed extraction-route decision contract, deterministic structure detection/strategy boundary, router node between chunking and extraction, route state/metrics, and fixture tests for table/repeated HTML/regex/semantic fallback. Prompt wording remains unchanged.
- Contracts affected: processed source/segment routing metadata, extraction method, deterministic strategy request/result envelope, and existing chunk-to-semantic extraction compatibility path.
- Required behavior: prefer deterministic CSS/XPath/table/regex only when configured or reliably detectable; route ambiguous prose to semantic structured generation; record method/reason; avoid any semantic model call for successful deterministic routes; fall back visibly when deterministic extraction is unsupported or fails.
- Validation order: routing rules and false-positive counterexamples, table/list/repeated-card/regex fixtures, semantic fallback, no-model-call proof, graph/state integration, frozen extraction benchmark comparison, full suite, then prior baselines/checks.
- Migration risks: Phase 15 multi-record output does not exist yet; Phase 14 must introduce routing without prematurely replacing the extraction contract or hard-coding domain-specific field mappings into the generic pipeline.

### Phase 17 — Field Evidence Contract

- Expected files: deterministic evidence-location helpers, an explicit graph node between extraction and merge, serializable evidenced-batch/metric/rejection state, downstream provenance preservation, frozen gold benchmark, and focused contract tests.
- Contracts affected: raw `extraction_batches` remain Silver candidates; `evidenced_extraction_batches` becomes the merge input; each populated retained field maps to canonical `EvidenceRef(source_url, chunk_id, evidence_text)` data.
- Required behavior: evidence text must be an exact slice of supplied chunk content; unsupported optional values follow nullable null versus non-nullable omit semantics; unsupported required values quarantine the record; evidence survives merge, validation, deduplication, and export.
- Validation order: exact/normalized-whitespace source binding, optional/required cases, deterministic cross-chunk binding, raw-candidate preservation, downstream JSON survival, frozen 8-page/12-record benchmark, full suite, then prior baselines/checks.
- Migration risks: evidence origin alone does not prove semantic entailment or contradiction; those acceptance statuses and final quality components belong to Phase 18 and must not be inferred from extractor confidence.

### Phase 18 — Evidence Validation and Quality Gate

- Expected files: typed verification/status/quality contracts, an `evidence_validation_node` after field binding, deterministic source/chunk/schema/type/evidence checks, configurable acceptance gate, metrics, and frozen supported/partial/unsupported/contradicted cases.
- Contracts affected: evidenced extraction candidates become `verified_records`; only gate-accepted records may continue toward Gold, while raw and evidenced Silver layers remain intact.
- Required behavior: separate extraction from acceptance, assign `SUPPORTED`, `PARTIALLY_SUPPORTED`, `UNSUPPORTED`, or `CONTRADICTED`, compute quality from measurable evidence/provenance/source/duplicate components, and never use extractor confidence as final quality.
- Validation order: typed checks, status boundaries, quality components, source-score fallback, optional semantic verifier isolation, graph/downstream acceptance, unsupported accepted-field-rate benchmark, full suite, then all earlier baselines/checks.
- Migration risks: Phase 19 owns cross-source resolution and Phase 20 owns upgraded deduplication; Phase 18 must expose duplicate state without implementing those later algorithms early.

### Phase 19 — Cross-Source Record Resolution

- Expected files: approved-schema identity declaration, typed contributor/provenance fields, a dedicated `record_resolution_node`, graph migration from legacy same-source merge, frozen multi-source benchmark, and explicit/composite/fallback tests.
- Contracts affected: optional `identity_fields`, `resolved_records`, source-scoped contributor objects, all source URLs/titles, field evidence, quality assessments, resolution method/key, and unresolved conflict details.
- Required behavior: resolve by explicit schema identity, conservative normalized generic identity, or configured composite identity; never merge identity-missing candidates; preserve every source/evidence/contributor/conflict; retain existing confidence conflict behavior.
- Validation order: identity schema validation, explicit cross-source merge, normalized fallback, composite key, missing/no-identity separation, conflict/provenance survival into metadata, frozen benchmark, full suite, then prior baselines/checks.
- Migration risks: record resolution is not duplicate removal; Phase 20 still owns URL/content hash and exact normalized-record dedup stages, and semantic similarity remains deferred.

### Phase 20 — Deduplication Upgrade

- Expected files: staged duplicate classification, canonical source/content hash index, exact normalized record fingerprint, schema-aware identity duplicate handling, provenance merge, metrics, and frozen duplicate-rate benchmark.
- Contracts affected: resolved/accepted record metadata gains duplicate stage/fingerprint/references while final `accepted_records` remains the exporter input.
- Required behavior: apply stages in canonical order, retain the strongest/evidence-complete representative without losing provenance, keep non-duplicates distinct, and do not add semantic/vector near-duplicate detection.
- Validation order: URL/hash duplicates, exact records, schema identities, collision counterexamples, provenance union, stable ordering/idempotence, benchmark exact duplicate rate, full suite, then all earlier baselines/checks.
- Migration risks: cross-source resolution may already combine legitimate same-identity contributors; dedup must not discard its conflicts/evidence or treat every shared URL as a duplicate record.
